Toutes les modifications notables de `aloli-crystal/pdf-tools`
sont documentées ici. Le format suit
https://keepachangelog.com/1.1.0/[Keep a Changelog] et le
versioning suit https://semver.org/[SemVer]
(3 chiffres pour création, 4 pour portage de gem Ruby).

== v0.9.0 — 2026-06-06 — Sous-commandes `toppm` et `tocairo` (rasterizer natif)

=== Ajouté

* **Sous-commande `toppm`** → `pdftoppm` et **sous-commande `tocairo`**
  → `pdftocairo` (rendre les pages d'un PDF en PNG/PPM via le rasterizer
  natif `PDF::Raster` — sans ghostscript). Shell-outs résolus via
  `$ALOLIPDF_TOPPM` / `$ALOLIPDF_TOCAIRO` puis le `PATH`.
* **Tout l'ensemble des poppler-utils est désormais accessible via
  `alolipdf`** : `info`, `fonts`, `detach`, `attach`, `images`, `tops`,
  `text`, `tohtml`, `toppm`, `tocairo` (externes) + `combine`,
  `validate`, `sign`, `verify`, `watermark` (in-process). (Le rendu
  raster est au stade MVP — vectoriel uniquement.)

== v0.8.0 — 2026-06-05 — Sous-commandes `text` et `tohtml` (pdf2text, pdftohtml)

=== Ajouté

* **Sous-commande `tohtml`** → `pdftohtml` (convertir un PDF en HTML
  positionné), et **sous-commande `text`** → `pdf2text` (extraire le
  texte positionné, `--json` / `--pages`). Outils externes nommés
  d'après poppler, donc en shell-out, résolus via `$ALOLIPDF_TOHTML` /
  `$ALOLIPDF_TEXT` puis le `PATH`.
* Avec elles, tout l'ensemble des poppler-utils portés par ALOLI est
  accessible via `alolipdf` : `info`, `fonts`, `detach`, `attach`,
  `images`, `tops`, `text`, `tohtml` (externes) plus `combine`,
  `validate`, `sign`, `verify`, `watermark` (in-process).

== v0.7.0 — 2026-06-05 — Sous-commande `tops` (pdftops)

=== Ajouté

* **Sous-commande `tops`** → `pdftops` (convertir un PDF en
  PostScript / EPS, relais ghostscript). Comme les autres outils
  nommés d'après poppler, elle reste en shell-out, résolue via
  `$ALOLIPDF_TOPS` puis le `PATH`. `pdftops` est fourni par le shard
  `ghostscript` (il pilote `gs`, ce n'est pas de la génération
  PostScript native).

== v0.6.0 — 2026-06-05 — Sous-commande `attach` (pdfattach)

=== Ajouté

* **Sous-commande `attach`** → `pdfattach` (joindre un fichier à un
  PDF — `/EmbeddedFiles` + `/AF`, Factur-X). Comme les autres outils
  nommés d'après poppler, elle reste en shell-out, résolue via
  `$ALOLIPDF_ATTACH` puis le `PATH`. Tout le flux de fichiers
  embarqués (`detach`/`attach`/`images`) est désormais accessible via
  `alolipdf`.

== v0.5.0 — 2026-06-05 — Sous-commande `images` (pdfimages)

=== Ajouté

* **Sous-commande `images`** → `pdfimages` (lister et extraire les
  images d'un PDF : `--list`, `--save-all`). Comme les autres outils
  nommés d'après poppler, elle reste en shell-out, résolue via
  `$ALOLIPDF_IMAGES` puis le `PATH`.

== v0.4.0 — 2026-06-05 — Sous-commande `detach` (pdfdetach)

=== Ajouté

* **Sous-commande `detach`** → `pdfdetach` (lister et extraire les
  fichiers embarqués d'un PDF : `--list`, `--save N`, `--save-all`).
  Comme `info` et `fonts`, c'est un outil externe nommé d'après
  poppler, donc il reste en shell-out, résolu via `$ALOLIPDF_DETACH`
  puis le `PATH`.

== v0.3.0 — 2026-06-05 — Méga-binaire compilé (outils ALOLI in-process)

=== Modifié

* **`alolipdf` est désormais un seul méga-binaire compilé**, plus un
  dispatcher shell-out. Les outils Crystal ALOLI sont liés et appelés
  *en interne* via le `Cli.run(argv) : Int32` de chaque outil :
** `combine` → `CombinePDF::Cli`, `validate` → `PDF::Validate::CLI`,
   `sign`/`verify` → `PDF::Signature::Cli`, `watermark` → `Watermark::Cli`.
* Rendu possible par la mise à niveau de toute la suite sur `pdf` 1.x
  (combine-pdf 1.0.31.40, watermark 0.1.6, validate 0.47, sign 0.12 —
  tous sur pdf 1.6) et l'exposition d'un `Cli.run` appelable par chaque
  outil. Plus de sous-processus, **plus de binaires ALOLI séparés à
  installer**.
* **Hybride par nécessité** : `info` (`pdfinfo`) et `fonts` (`pdffonts`)
  de poppler ne sont pas du code ALOLI ; ils restent en shell-out
  (résolus via `$ALOLIPDF_INFO` / `$ALOLIPDF_FONTS` puis le `PATH`).
* `doctor` indique désormais les cinq outils ALOLI comme « compilé dans
  alolipdf (in-process) » et ne vérifie sur le `PATH` que les deux
  outils externes.

=== Ajouté

* Dépendances sur les quatre outils ALOLI, requis par leurs chemins
  `src/` et appelés en interne (`Tool#runner`).

== v0.2.0 — 2026-06-05

=== Ajouté

* **Deux nouvelles sous-commandes** branchant les outils de
  métadonnées PDF dans le dispatcher :
** `info` → `pdfinfo` (métadonnées du document : titre, dates, pages,
   version…),
** `fonts` → `pdffonts` (liste des fontes : type, encodage, embarquée,
   sous-ensemble).
* Binaires résolus comme d'habitude via `$ALOLIPDF_INFO` /
  `$ALOLIPDF_FONTS` puis le `PATH` ; les deux apparaissent dans
  `alolipdf help` et `alolipdf doctor`.

== v0.1.0 — 2026-06-05

=== Ajouté

* Création du shard à partir du template
  https://github.com/aloli-crystal/shard-template[aloli-crystal/shard-template].
* **Dispatcher `alolipdf`** (`AloliPdf::Dispatcher`) — façade unifiée sur
  la suite PDF ALOLI. Chaque sous-commande relaie au binaire autonome
  correspondant, en héritant de la sortie et du code de retour :
** `combine` → `crystal-combine-pdf`, `validate` → `pdf-validate`,
   `sign` → `pdf-sign sign`, `verify` → `pdf-sign verify`,
   `watermark` → `watermark`.
* Commandes intégrées `help [<outil>]`, `version` et `doctor` (indique
  quels outils sous-jacents sont installés).
* Résolution du binaire par outil : `$ALOLIPDF_<OUTIL>` (chemin explicite)
  puis le nom sur le `PATH`. Tout ce qui suit la sous-commande est relayé
  tel quel, donc les secrets (p. ex. la phrase de passe de pdf-sign passée
  par nom de variable d'env) ne transitent jamais par argv via cette
  couche.
* Choix de conception : shell-out plutôt que liaison des shards (versions
  de `pdf` incompatibles). Cf. `doc/INSTALLER.adoc` pour la feuille de
  route d'empaquetage.
* Module `AloliPdf` avec `VERSION` lue au compile-time depuis `shard.yml`.
